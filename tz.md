# ТЗ: картировка тендерной номенклатуры на номенклатуру LD

## 1. Цель

Реализовать MVP-сервис семантического сопоставления текстовых наименований номенклатуры с товарами из базы LD.

На вход сервис получает **список строк с номенклатурой**.

Пример:

```python
[
    "Кран шаровой Ридан JiP-R Standard FF Ду80 Ру16 стандартнопроходной",
    "Кран шаровой сталь JiP-R Standard FF Ду 80 Ру16 фл Ридан",
    "Кран шаровой FF DN80 PN16",
    "Кран латунный шаровой муфтовый Д25",
    "Фланцы стальные",
    "Арматура трубопроводная фланцевая",
]
```

Для каждой строки необходимо найти наиболее подходящий товар из номенклатуры LD.

Результатом является картировка:

```text
исходная номенклатура
        →
товар LD
```

либо:

```text
исходная номенклатура
        →
NOT_FOUND
```

если достаточно подходящего товара не найдено.

---

## 2. Что является входом

Вход MVP:

```python
list[str]
```

Например:

```json
[
  "Кран шаровой Ридан JiP-R Standard FF Ду80 Ру16",
  "Кран шаровой FF DN80 PN16",
  "Кран латунный шаровой муфтовый Д25"
]
```

На данном этапе сервису не нужно знать:

* tender_id;
* run_id;
* документ-источник;
* количество;
* единицу измерения;
* confidence извлечения;
* структуру Excel.

Обрабатывается только текст номенклатуры.

---

## 3. Общий пайплайн

```text
Список номенклатур
        │
        ▼
[
  query_1,
  query_2,
  query_3,
  ...
]
        │
        ▼
Для каждого query
        │
        ▼
Embedding
        │
        ▼
Vector Search по индексу LD
        │
        ▼
TOP-K кандидатов
        │
        ▼
Best candidate
        │
        ▼
Similarity threshold
        │
        ├── score >= threshold
        │        ↓
        │     MATCHED
        │
        └── score < threshold
                 ↓
              NOT_FOUND
        │
        ▼
Список результатов
```

---

## 4. База для поиска

Источник — PostgreSQL с номенклатурой LD.

Используем следующие данные:

```text
id
name
article
price
dn
pn
joining_type
url
properties_json
```

Для каждого товара LD заранее формируется текстовый документ и embedding.

Пример документа:

```text
Кран шаровый 11с67п КШРФ из стали 20 Ду80 Ру1,6МПа полнопроходной

Артикул: ...
DN: 80
PN: 1,6
Присоединение: фланцевое
Материал корпуса: Сталь 20
Тип продукта: Кран шаровой
...
```

В документ включаются:

```text
name
article
dn
pn
joining_type
properties_json
```

Служебные данные в embedding не включаются.

---

## 5. Индексация

Номенклатура LD индексируется заранее.

```text
PostgreSQL
     ↓
LD products
     ↓
формирование search_text
     ↓
embedding
     ↓
Qdrant
```

При каждом пользовательском поиске повторно векторизовать всю базу LD не нужно.

---

## 6. Поиск

Для каждой входной строки:

```python
query = nomenclature
```

выполняется:

```text
query
 ↓
embedding
 ↓
Qdrant
 ↓
TOP-K
```

На первом этапе используется исходная строка целиком.

Не выполняются:

* извлечение DN;
* извлечение PN;
* извлечение материала;
* определение типа продукта;
* LLM-анализ;
* StructuredQuery.

---

## 7. Результат

На каждую входную строку возвращается отдельный результат.

Пример:

```json
[
  {
    "query": "Кран шаровой FF DN80 PN16",
    "status": "MATCHED",
    "score": 0.91,
    "ld_product": {
      "id": 1234,
      "article": "КШ....",
      "name": "Кран шаровый LD ... Ду80 Ру1,6МПа",
      "dn": 80,
      "pn": "1,6",
      "joining_type": "Фланцевое",
      "price": 15000,
      "url": "..."
    }
  },
  {
    "query": "Арматура трубопроводная фланцевая",
    "status": "NOT_FOUND",
    "score": 0.54,
    "ld_product": null
  }
]
```

---

## 8. Формат картировки

По сути сервис должен строить структуру:

```python
{
    "<исходная номенклатура>": "<найденный товар LD>"
}
```

Но технически предпочтительно возвращать список объектов, потому что он позволяет хранить:

* статус;
* score;
* ID;
* артикул;
* название;
* дополнительные данные товара.

---

## 9. TOP-K

Поиск должен получать не только первый результат, а несколько кандидатов.

Начальное значение:

```text
TOP_K = 5
```

Например:

```text
Кран шаровой FF DN80 PN16

1. LD product A — 0.92
2. LD product B — 0.88
3. LD product C — 0.79
4. LD product D — 0.63
5. LD product E — 0.59
```

В основной результат возвращается первый кандидат, если его score превышает threshold.

TOP-K сохраняется для отладки и оценки качества поиска.

---

## 10. Threshold

Необходимо иметь:

```text
MATCH_THRESHOLD
```

Если:

```text
best_score >= MATCH_THRESHOLD
```

результат:

```text
MATCHED
```

Если:

```text
best_score < MATCH_THRESHOLD
```

результат:

```text
NOT_FOUND
```

Threshold подбирается экспериментально на реальных примерах.

---

## 11. Дубли

Если во входном списке одинаковая номенклатура встречается несколько раз, достаточно выполнить поиск один раз.

Например:

```python
[
    "Кран шаровой FF DN80 PN16",
    "Кран шаровой FF DN80 PN16",
    "Кран шаровой FF DN80 PN16"
]
```

может быть обработан как один уникальный запрос.

Полученная картировка затем может быть использована для всех одинаковых строк.

---

## 12. Что НЕ входит в текущую задачу

На данном этапе не реализовывать:

* загрузку tender Excel;
* изменение `result.xlsx`;
* интеграцию с `/ui/runs`;
* изменение существующего tender pipeline;
* работу с количеством;
* работу с единицами измерения;
* LLM;
* извлечение характеристик;
* hard filters по DN/PN;
* правила совместимости материалов;
* rule-based reranking;
* UI.

Сначала необходимо отдельно решить задачу:

```text
list[nomenclature]
        ↓
semantic search
        ↓
mapping на LD
```

и проверить качество такого подхода.

---

## 13. MVP

Минимальная первая версия:

```python
queries = [
    "...",
    "...",
    "..."
]

results = matcher.match(queries)
```

где:

```python
results = [
    {
        "query": "...",
        "status": "MATCHED",
        "score": 0.91,
        "ld_product": {...}
    },
    ...
]
```

Архитектурно:

```text
LD PostgreSQL
     ↓
Indexer
     ↓
Embedding model
     ↓
Qdrant


list[str]
     ↓
Matcher
     ↓
Embedding model
     ↓
Qdrant TOP-K
     ↓
Threshold
     ↓
MATCHED / NOT_FOUND
```

Это и является первой задачей проекта.
