# Следующий шаг: Eval V2 на новой реальной номенклатуре

## Цель

Собрать второй, более полезный human-reviewed eval-набор на основе нового файла номенклатуры:

```text
kontur_AP123184_nomenclature.xlsx
```

В файле 43 строки данных. Для основного eval нужно взять только товарные и технически информативные позиции.

Главная цель wave:

```text
не улучшать retrieval
не менять reranker
не добавлять правила поиска

а сначала получить хороший eval V2
```

После этого измерить текущий pipeline:

```text
Dense TOP-20
BM25 TOP-20
Hybrid TOP-20
DeepSeek reranker
```

и только по результатам решать, что менять дальше.

# 1. Главный принцип соответствия

Нельзя делать strict string matching.

Нужно проверять технический смысл запроса.

Правило:

```text
Явно указанная техническая характеристика -> обязательна.
Эквивалентная формулировка того же смысла -> допустима.
Не указанная характеристика -> не должна становиться hard constraint.
Явное противоречие характеристике -> товар НЕ acceptable.
```

Примеры эквивалентных обозначений:

```text
DN100 ~= Ду100 ~= номинальный диаметр 100 мм
PN16 ~= Ру16 ~= 1,6 МПа
встык ~= приварной в стык
НР/ВР ~= наружная/внутренняя резьба
```

Не требовать буквального совпадения слов.

Но НЕ считать эквивалентными технически разные варианты:

```text
межфланцевый != фланцевый
фланцевый != приварной
DN150 != DN250
PN16 != PN25
латунь != сталь
ПНД != сталь
муфтовый != фланцевый
```

---

# 2. Правило optional vs explicit attributes

Если запрос:

```text
Кран шаровой DN80 PN16
```

то обязательны:

```text
тип = кран шаровой
DN = 80
PN = 16
```

Но пользователь не указал:

```text
материал
рабочую среду
подземное/надземное исполнение
тип управления
```

Поэтому эти свойства не являются hard constraints.

При этом специальное исполнение без запроса пользователя может быть менее предпочтительным.

Например обычный кран предпочтительнее подземного Gas-варианта для общего запроса.

Но это preference, а не причина автоматически считать товар неправильным, если других противоречий нет.

Если же запрос явно говорит:

```text
в помещении
наружный, в колодце
подземный
газ
вода
```

тогда это уже обязательная характеристика.

# 3. Исправить старый q04 перед Eval V2

Старый запрос:

```text
Затвор дисковый межфланцевый Ду150 Ру16
```

Текущий golden загрязнён.

В acceptable_ld_ids НЕ должны находиться товары с:

```text
DN250
PN25
приварным присоединением
```

Даже если пользователь ранее отметил их в широком списке.

Отдельно:

```text
межфланцевый != фланцевый
```

Если в каталоге есть реально межфланцевое решение DN150 PN16 — только оно может считаться строгим match.

Если его нет, НЕ объявлять фланцевый товар правильным автоматически.

Такой query можно оставить VERIFIED только после human confirmation найденного товара.

До подтверждения допускается:

```text
q04 -> UNREVIEWED
```

# 4. Новый eval не должен содержать все строки Excel

Не брать в основной matching eval строки, которые описывают монтаж/работу, например:

```text
Установка стальных фланцев Ду 100
Смена кранов муфтовых диаметром 15 мм
Монтаж затвора ду100 мм
Монтаж задвижки Ду50мм
Монтаж крана шарового ду80 мм
Установка кранов на трубопроводах...
```

Это не чистая товарная номенклатура.

Не брать слишком общий запрос:

```text
Трубопроводная арматура
```

Для него нет честного единственного товарного ответа.

Такие строки можно сохранить отдельно как future scope, но НЕ включать в основные retrieval metrics.

# 6. Не создавать golden labels автоматически

Модель НЕ должна сама выбирать правильные LD товары как истину.

Нельзя использовать:

```text
DeepSeek selected result -> golden
Dense TOP-1 -> golden
BM25 TOP-1 -> golden
Hybrid TOP-1 -> golden
```

Это evaluation leakage.

Сначала нужно получить candidate report для human review.

---

# 7. Сделать script для подготовки human-review отчёта

Добавить:

```text
scripts/prepare_eval_v2_review.py
```

Он должен для каждого query:

1. выполнить dense retrieval;
2. выполнить BM25 retrieval;
3. выполнить hybrid retrieval;
4. НЕ вызывать DeepSeek как judge для создания labels;
5. собрать уникальный пул кандидатов из TOP результатов;
6. вывести технические поля кандидатов.

Рекомендуемый candidate pool:

```text
Dense TOP-10
BM25 TOP-10
Hybrid TOP-10
union + dedupe by ld_id
```

Для каждого кандидата сохранить:

```json
{
  "ld_id": 123,
  "article": "...",
  "name": "...",
  "dn": "...",
  "pn": "...",
  "joining_type": "...",
  "dense_rank": 3,
  "bm25_rank": null,
  "hybrid_rank": 5
}
```

Если доступны основные properties, добавить только полезные для проверки:

```text
Тип продукта
Материал корпуса
Присоединение
DN
PN
Рабочая среда
Управление
Тип резьбы
Тип прохода
Серия
```

Не печатать весь properties_json.

Сохранить:

```text
data/eval_v2_review_candidates.json
```

# 8. Human labels V2

Создать пустой шаблон:

```text
data/eval_labels_v2.json
```

Для каждого query первоначально:

```json
{
  "label_status": "UNREVIEWED",
  "acceptable_ld_ids": [],
  "expected_status": null,
  "human_comment": ""
}
```

Не заполнять acceptable IDs автоматически.

Пользователь вручную посмотрит `eval_v2_review_candidates.json` и отметит acceptable товары.

---

# 9. Добавить поле rejection reason только в human-review artifact

Для удобства human review допускается шаблон:

```json
{
  "ld_id": 123,
  "human_grade": null,
  "human_comment": ""
}
```

Где:

```text
2 = соответствует запросу
1 = технически близкий, но не строгий match
0 = противоречит явно указанным характеристикам
```

Основная retrieval метрика считается по grade=2.

Grade=1 можно использовать отдельно как диагностическую статистику, но НЕ считать strict success.

---

# 10. После human review сделать Eval V2 runner

Только после заполнения `eval_labels_v2.json` добавить или расширить eval runner так, чтобы он мог запускаться отдельно:

```bash
python scripts/eval.py --queries data/eval_queries_v2.json --labels data/eval_labels_v2.json --output data/eval_results_v2.json
```

Если текущий `eval.py` не поддерживает эти аргументы, добавить минимальные CLI options.

Старый eval должен продолжить работать без аргументов.

Не переписывать evaluation architecture.

# 11. Метрики Eval V2

Считать только VERIFIED queries.

Обязательные метрики:

```text
Dense Recall@20
BM25 Recall@20
Hybrid Recall@20
Reranker Accuracy
Reranker Accuracy given Hybrid Hit
```

Дополнительно вывести:

```text
Dense-only hits
BM25-only hits
Both hit
Neither hit
Hybrid recovered dense miss
```

Особенно важная метрика:

```text
Hybrid recovered dense miss
```

Она должна показать, действительно ли BM25 даёт пользу поверх dense.

---

# 12. Error classification

Для каждого VERIFIED query:

```text
OK
HYBRID_RETRIEVAL_FAIL
RERANKER_FAIL
RERANKER_ERROR
CORRECT_NOT_FOUND
WRONG_NOT_FOUND
```

Дополнительно в diagnostics сохранить:

```text
dense_hit
bm25_hit
hybrid_hit
```

Сценарий:

```text
dense miss
bm25 hit
hybrid hit
reranker correct
```

должен классифицироваться как:

```text
OK
```

и одновременно учитываться в `hybrid_recovered_dense_miss`.

# 14. Что НЕ делать в этом wave

НЕ добавлять:

- DN/PN parser в production retrieval;
- StructuredQuery;
- LLM attribute extraction;
- hard filters;
- synonym dictionaries;
- fuzzy article matching;
- новые embeddings;
- Qdrant sparse vectors;
- Elasticsearch/OpenSearch;
- reranker prompt changes;
- reranker model changes;
- BM25 tokenizer improvements;
- production API;
- Kafka;
- database changes.

Сначала собрать нормальный Eval V2 и измерить текущую систему.

---

# 15. Definition of Done

Wave завершён, если:

1. создан `data/eval_queries_v2.json` из 10-12 информативных товарных запросов;
2. монтажные/слишком общие строки не включены в основной eval;
3. создан `scripts/prepare_eval_v2_review.py`;
4. создан `data/eval_v2_review_candidates.json`;
5. candidate report содержит технические поля, но не огромный raw properties_json;
6. создан `data/eval_labels_v2.json` со статусом UNREVIEWED по умолчанию;
7. модель НЕ придумала golden labels самостоятельно;
8. старый q04 очищен или переведён в UNREVIEWED до human confirmation;
9. существующий retrieval/reranker не изменён;
10. тесты проходят;
11. после подготовки human-review данных работа останавливается.

Не оптимизировать поиск дальше до ручной разметки Eval V2.
