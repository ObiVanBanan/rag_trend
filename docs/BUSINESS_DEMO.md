# Демо подбора тендерных аналогов LD (16 октября 2026)

Демо добавлено к существующей production ветке `codex/competitor-resolver-v2`; алгоритм поиска и публичный `POST /v1/match` не меняются.

## Запуск

1. Выполнить `git lfs pull`, заполнить `.env` (OPENAI_API_KEY, DEEPSEEK_API_KEY, POSTGRES_PASSWORD, PUBLIC_DEMO_PASSWORD), проверить наличие индекса Qdrant. В production запросы без пароля блокируются.
2. Выполнить `docker compose -f docker-compose.yml up -d --build`. Это предотвращает автоподключение observability override (порт 8002).
3. Проверить `http://localhost:8000/health/ready`; открыть `http://localhost:8000/demo`.
4. Swagger: `http://localhost:8000/docs`, бизнес endpoint: `POST /v1/demo/match`, вход `{"products":["Кран шаровой Ду50 Ру16"]}`.
5. Фокус показа: вставить номенклатуру → увидеть компактную таблицу «исходный запрос / рекомендуемый LD / артикул / статус» → раскрыть «Подробнее» для инженерной сверки и неподтверждённых альтернатив. `INSUFFICIENT_PARAMETERS` показывает, какие сведения запросить у заказчика. Веб-интерфейс не выводит retrieval score, confidence, latency и benchmark-метрики. Расхождение/отсутствие данных по одному критичному полю не должно маскироваться утверждением о подтверждённом соответствии.
6. Для белого IP использовать Caddy + HTTPS; адрес публикации Docker по умолчанию локальный. Инструкция: `docs/PUBLIC_SERVER_DEPLOY_RU.md`.

## Обновлённый веб-интерфейс (PR #20)

- Фирменная светлая рабочая область и чёрно-жёлтая шапка LD; знак LD реализован текстом без внешних CDN или загрузок. Для точного корпоративного логотипа позже заменить mark на официальный брендовый SVG.
- На \`/demo\` можно вставить до **10** тендерных строк, по одной позиции на строку. Пустые строки пропускаются, длина одной позиции не более 2000 символов.
- Файлы **CSV, TSV, TXT** до **1 МБ** разбираются локально в браузере. Понимается UTF-8 и Windows-1251; CSV-таблицы с колонкой «Наименование / Номенклатура / Строка сметы / Позиция» извлекаются как строки номенклатуры. Прямая загрузка .xlsx **не поддерживается**: пользователю предлагается вставить столбец из Excel. Никогда не показывать кнопку импорта XLSX до реализации сервера/клиентского парсера.
- Результаты в таблице и раскрывающиеся пояснения. \`MATCHED\` — предварительный кандидат. Внутри: таблица «требование → факт LD → статус», источником фактов служит текущий catalog DTO. Другие кандидаты явно помечены как **не подтверждены**.
- \`INSUFFICIENT_PARAMETERS\` отображает \`missing_fields\` в человекочитаемой форме, отдельно от \`NOT_FOUND\` и \`ERROR\`. Поля \`flange_kind\`, \`stub_dn\`, \`thread_size\` представлены по-русски.
- История **последних 15 запусков** теперь содержит снимок **каждого запроса и каждого ответа**: названия, артикулы, статус, допустимые кандидаты, сравнение технических характеристик и пользовательские решения. Хранится в `localStorage` браузера; `review_token`, API-ключи, GOLD и технические метрики туда не пишутся. После обновления страницы старый ответ доступен для просмотра **без вызова LLM** (read-only), новый подбор запускается отдельно. Кнопка «Очистить историю» стирает все снимки. На общем компьютере обязательно очищать чувствительные тендерные данные.
- При недоступной истории (private browsing/storage blocked) подбор продолжает работать.
- API остаётся \`POST /v1/demo/match\` и не подвергается изменениям качества поиска; на production-доступ к интерфейсу и платным API защищён Basic auth.
- Контракт/JS синтаксис: \`uv run python -m pytest -q tests/test_business_demo_ui.py tests/test_business_demo.py\`. Node.js используется для локального синтаксического контроля JavaScript, если установлен.

## Добавление забытой позиции без повторного подбора (PR #25)

После запуска списка из 1–10 товаров нажмите **«＋ Добавить позицию»** над результатами. В открывшейся форме укажите одну новую исходную строку и/или заполните её технические характеристики (тип изделия, DN, PN в МПа, присоединение, штуцерное исполнение, среду, размер резьбы, материал, проход и т. д.). Нажмите **«Найти и добавить товар»**.

- API `POST /v1/demo/append` запускает `match_one_hybrid_with_rerank` **только для одной новой позиции**. Предыдущие строки, исправления и принятые/отклонённые аналоги не вычисляются заново.
- Новая строка добавляется в текущую таблицу с собственными top-10, редактированием и ручным выбором. Лоток «найдено / всего» обновляется автоматически.
- Список сохраняет первоначальный `request_id` и review token **только в оперативной памяти вкладки**. PostgreSQL транзакционно добавляет строку с новым индексом; номер первоначального товара и его решения не меняются. Событие `ITEM_ADDED` отражено в закрытой аналитике.
- Исходный batch-лимит — 10 за один `POST /v1/demo/match`; через `append` можно последовательно добавить до общего лимита **100** товаров в одном сеансе. Это ограничение распространяется на сохранённую историю снимков. Если открыть архив после перезагрузки страницы, он доступен для просмотра, но продолжить редактирование старого сеанса нельзя без нового review token.
- Отдельно указанные характеристики используются как явные факты при формировании нового технического запроса. Если пользователь вводит только текст, matcher интерпретирует его по стандартной схеме. `11Б27П` без необходимых технических характеристик по-прежнему получает `INSUFFICIENT_PARAMETERS`.
- При одновременном добавлении через две вкладки устаревшее `expected_count` даёт `409 Conflict`, а не дублирует или затирает товар. Новая позиция не создаёт GOLD-ответов и не снижает требования технической совместимости.

Проверка: запустить исходные семь строк, добавить восьмую — «Кран шаровой штуцерный Ду20 Ру40», выбрать `Штуцерное`, задать DN20 и PN4.0 МПа и подтвердить. Должна появиться восьмая строка; старые семь не должны измениться, история должна показывать все восемь ответов без повторного API-запроса.

```bash
uv run pytest -q tests/test_demo_append_item.py tests/test_demo_feedback_postgres.py
```

Тест PostgreSQL требует `TEST_DEMO_PG_DSN`, в GitHub Actions временная Postgres-среда создаётся автоматически. Браузерный test `tests/test_demo_ui_browser.py` использует Chromium, проверяет добавление и повторное открытие истории без повторной обработки.

## Reference UX v2 — PR #23

- Нажать «Кандидаты (N)» в строке результата; первый результат с кандидатами раскрывается автоматически.
- Рекомендованное LD изделие представлено отдельной карточкой с артикулом и проверяемыми характеристиками; справа сразу видны поля для корректировки DN/PN/материала/присоединения/ПНД.
- Ниже находится **видимая без дополнительного раскрытия таблица кандидатов**. Если поиск вернул 2 изделия, отображаются 2, если 10 — 10. Никаких выдуманных товаров для добивки числа до десяти.
- Нажать «Выбрать» рядом с другой технически допустимой позицией: отправится `SELECTED_OTHER`, её LD-артикул появится прямо в общей таблице и в текущем снимке истории. Несовместимые кандидаты помечаются «Есть расхождения» и недоступны к выбору; неизвестные параметры требуют ручного подтверждения.
- Открыть «История» после обновления страницы и выбрать сохранённый запуск — видеть **все исходные строки и их ответы**, без повторного поиска. Из архива можно просмотреть альтернативы, но менять старый результат нельзя. Старые query-only записи v2 не преобразуются задним числом в результат.
- Бизнес-статистика дополнена четырьмя графиками, основанными на реальной БД: stacked daily status bar, распределение исходных статусов, временные ряды событий и горизонтальная сравнительная диаграмма действий.
- Браузерный e2e-тест на Chromium проверяет выбор другого артикула, сохранение после reload, корректный read-only просмотр истории и отображение графиков. Screenshot artifacts доступны в GitHub Actions.

## Feedback MVP: исправления, выбор LD и статистика

### Пользовательский сценарий

На \`/demo\` пользователь загружает до 10 строк (как раньше). Для каждой позиции:
1. Видит рекомендованное LD изделие и артикул, либо причину отказа.
2. Нажимает **Подробнее** → **Исправить извлечённые характеристики**. Изменяет DN, PN (в МПа), материал, среду, резьбу, исполнение или размер ПНД-втулки. **Применить и подобрать заново** делает новый вызов текущего production matcher; исходные тендерные формулировки остаются записанными отдельно. \`11Б27П\` по-прежнему требует среду, тип и размер резьбы; исходные запреты и \`HARD_CONSTRAINT_FILTER\` не отключаются.
3. Может **Принять рекомендацию**, **Отклонить результат**, либо **Выбрать этот LD** в списке до 10 найденных кандидатов. Ручной выбор из других кандидатов НЕ является автоматическим \`MATCHED\`; он маркируется как пользовательский. Кандидат с расхождением по строгим полям отклоняется сервером (HTTP 409). Неизвестные/недоказанные строгие характеристики требуют отдельного подтверждения человеком.
4. Под таблицей доступна сверка с каталогом, исходная интерпретация и другие (пока не подтверждённые) кандидаты.
5. Инженерный «лоток изделий» показывает найденные автоматически позиции из общего числа и **отдельно** число подтверждённых пользователем; не приравнивает найденное к верному.
6. История теперь сохраняет полный бизнес-снимок запроса/ответа (все строки, LD-артикулы, технические проверки, доступные кандидаты, решения пользователя), но не review-token. Старые записи формата v2 содержат только тексты, восстановить утраченные результаты задним числом нельзя.

**Важно:** данный UX не допускает тихого изменения результата. Исправление характеристик повторно запускает matcher и создаёт событие \`PARAMETERS_CORRECTED\`. Альтернативный выбор создаёт \`SELECTED_OTHER\`, принятие — \`ACCEPTED\`, отклонение — \`REJECTED\`. События не используются как GOLD/обучающие примеры автоматически.

### Сохранение решений

Таблицы PostgreSQL создаются автоматически при инициализации существующего \`PostgresRequestHistory\`:
- \`demo_review_sessions\` — запуск демо с одноразовым секретом (в базе только SHA-256);
- \`demo_review_rows\` — исходный ответ, текущий ответ после коррекции, ревизия и последнее решение;
- \`demo_review_events\` — неизменяемые события действий человека.

Используется уже существующая \`DATABASE_URL\`, отдельного сервиса или таблиц benchmark не нужно. \`review_token\` возвращается только на запрос \`POST /v1/demo/match\`, живёт в оперативной памяти вкладки и не помещается в URL/браузерную историю. После перезагрузки пользователь открывает сохранённый снимок без API и без трат на LLM, но **редактирование снимка запрещено**: чтобы редактировать, нужно запустить новый подбор с новой защищённой сессией.

### Метрики для бизнеса

В рабочем UI метрики не показываются. Администратору доступны отдельные \`GET /demo/stats\` и \`GET /v1/demo/stats?days=30\` (1–366 дней). Для доступа требуется настроить отдельную пару Basic Auth в \`.env\`:

\`\`\`env
PUBLIC_DEMO_ADMIN_USERNAME=ld-admin
PUBLIC_DEMO_ADMIN_PASSWORD=<случайный_длинный_секрет>
\`\`\`

Если пароль администратора пуст, статистика недоступна (доступ закрыт). Для входа из браузера используется отдельная HTTP Basic realm \`LD Tender Admin\`. Доступ только через HTTPS при публикации.

Счётчики: \`processed\`, \`auto_matched\`, \`not_found\`, \`insufficient\`, \`errors\` — статусы исходного поиска; \`accepted\`, \`rejected\`, \`selected_other\`, \`parameter_edited\`, \`pending\` — текущие состояния. Категории действий **не взаимоисключающие**: исправленный товар может затем быть принят. История событий \`demo_review_events\` считает клики за период, а состояние \`demo_review_rows\` — количество отдельных строк с соответствующей меткой.

**Никакой числовой процент не является реальной точностью RAG**, пока ответы не сопоставлены с независимыми GOLD и не проверены экспертами. Review из демо не изменяет frozen-100 и не обучает модель напрямую.

## Метрики и честные оговорки

- Поле `retrieved_count` — размер выдачи после поиска, а не точность.
- `recommended_count` — число выбранных ранжировщиком LD, а не доказательство совместимости.
- `score` — поисковый балл; `llm_confidence` — утверждение модели; **ни одно не является калиброванной вероятностью верного сопоставления**.
- `NOT_FOUND` означает, что pipeline не подтвердил совпадение, но не доказывает отсутствие товара во всём каталоге.
- Старый отчёт `data/harness_gold_eval.json` ветки `prod/rag-tender-exp4`: **16/19 (84,2%)** на 2026-09-08. Не выдавать за свежую оценку 20/100.
- Не путать `data/eval_queries_v2.json` (11 кейсов) с **оригинальной двадцаткой** `data/tender_queries_v1_harness_cases.json` (11 CORE + 9 EXTENDED) из ветки `prod/rag-tender-exp4`. Её mapping хранится в `data/tender_queries_v1_canonical_labels.json` там же; 20 подтверждённых положительных меток **неисчерпывающие**. Их попадание — нижняя граница технической полноты, не готовая точность.
- Необходимо перезапустить **оба** набора: 20 и 100 кейсов на выбранном коммите и фиксированном каталоге/моделях. Раздельно считать exact top1 / strict constraint pass, false match, wrong NOT_FOUND и latency p50/p95. Unreviewed и SILVER не подменять human-GOLD.
