# Подбор товарных аналогов LD для тендеров
**Описание текущего решения для демонстрации бизнесу • 14 октября 2026**

## Что делает система

Задача: уменьшить ручное время подбора аналогов LD к строкам чужих тендерных спецификаций. На вход система получает свободную текстовую номенклатуру, включая размеры, давления, материалы и в ряде случаев коды товаров конкурентов. На выходе — предложение LD с наименованием и артикулом. Подбор носит рекомендательный характер: технически спорные позиции должен подтвердить специалист.

**Это не просто поиск по совпадению слов.** Система интерпретирует характеристики оборудования, сопоставляет их с характеристиками каталога LD, ищет несколько вероятных товаров и отдельно ранжирует пригодность кандидатов.

## Логика работы: без технического жаргона

1. **Понимаем заявку.** Из строки выделяем тип изделия, DN, PN, тип присоединения, материал корпуса, тип прохода и управление. Неизвестные характеристики не выдаём за известные.
2. **Распознаём модель конкурента.** Если строка содержит чужое обозначение, resolver ищет точный профиль изделия в локальной базе/каталогах и отличает семейство от конкретной модификации.
3. **Ищем LD в каталоге.** Совмещаем смысловой поиск по векторному индексу Qdrant и текстовый BM25, объединяем списки методом RRF.
4. **Проверяем ограничения.** Сначала применяем явно заданные технические требования и структурную совместимость к широкому списку поиска, затем оставляем ограниченный пул для финального выбора.
5. **Ранжируем варианты.** LLM выбирает наиболее подходящие товары из короткого списка; возвращает имя, артикул и обоснование.
6. **Не уверены — не маскируем.** Если подтверждённого варианта нет, выдаём NOT_FOUND; ошибки внешних систем показываем отдельно. NOT_FOUND означает отсутствие подтверждённого результата в текущем пайплайне, а не гарантию отсутствия товара в LD.

## Техническая реализация

- Python/FastAPI; оригинальный batch endpoint: POST /v1/match.
- Embeddings: OpenAI; векторное хранилище: Qdrant; текстовое извлечение: BM25 in-memory; объединение RRF.
- Нормализация запроса и reranking: DeepSeek; hard-фильтрация и технический prefilter: Python.
- Resolver конкурентов использует локальные источники; runtime web-обогащение в фиксированном эксперименте E08 было отключено.
- API имеет метрики Prometheus, логирование этапов и историю production-запросов в PostgreSQL. Demo endpoint — отдельное представление для UI, не меняет production контракт. Не утверждать, что demo-запросы сохраняются в production PostgreSQL до отдельной проверки.

## Измерения: что реально подтверждено

**Исторический frozen-100 DEV, seed=53, эксперимент E08 (не повторная проверка текущего демо):**

| Метрика | E07-CAT | E08 |
| --- | ---: | ---: |
| Exact top-1 попадание в acceptable LD ID | 30/100 | **34/100** |
| Допустимый LD присутствует среди кандидатов reranker | 62/100 | **84/100** |
| Допустимый LD есть в широком поисковом пуле | 92/100 | **93/100** |
| Потерянные reranker'ом случаи при доступном GOLD | 31 | **50** |

В E08: 7 случаев отсутствия из широкого поиска, 9 потерь на technical prefilter, 50 выборов не-GOLD при наличии допустимого кандидата. В документации указаны четыре конфликта parsed constraints / mapping и две потенциально неполные GOLD-разметки; поэтому **34% — метрика точного попадания в текущий mapping, не доказанная точность технической эквивалентности**.

**Отдельный старый тест:** 16/19 (84,2%) hard pass на маленькой проверке (сохранён 8 сентября 2026). Нельзя объединять или сравнивать напрямую с exact-ID frozen-100. Оригинальные 20 реальных тендерных кейсов найдены в экспериментальной ветке `prod/rag-tender-exp4`: `data/tender_queries_v1_harness_cases.json` (11 CORE, 9 EXTENDED), GOLD-позитивы — в `data/tender_queries_v1_canonical_labels.json`. Выгрузить их из Git без внесения GOLD в production данные: `git fetch origin prod/rag-tender-exp4`, `python scripts/export_demo20_cases.py`, `python scripts/demo_recheck.py --cases .tmp/demo20_verified.json --out .tmp/demo20_results.json`. Human positives **неисчерпывающие**: known-positive hit на 20 не является полной метрикой качества аналогов.

## Что демонстрируем бизнесу

Открыть GET /demo; ввести позицию; показать понятные DN/PN/материал/присоединение; раскрыть рекомендованные LD (название, артикул, объяснение) и отдельно дополнительные **непроверенные** кандидаты. Три оперативных показателя экрана: задержка, размер поисковой выдачи и число рекомендаций. Не называть LLM confidence процентом качества.

К пятнице необходимо прогнать выбранный frozen-20 и frozen-100 на одной конфигурации, проверить реальные интеграции, снять latency p50/p95, показать несколько удачных и несколько сложных запросов. Сравнение с Codant допустимо только по одинаковым запросам, единому понятию допустимого аналога и одинаковым условиям проверки. Функциональность UI конкурента на https://ld-proto.codant.ru/#/spec пока не была подтверждена через доступный программный просмотр SPA.

**Вывод:** сильная сторона системы — структурный технический подбор и широкий поиск потенциальных аналогов. Основная текущая проблема — качество финального выбора: подходящий вариант часто присутствует в пуле, но ранжировщик выбирает другой. Бизнес-демо должно показывать прозрачный список предложений, а не обещать автоматическую замену инженера.
